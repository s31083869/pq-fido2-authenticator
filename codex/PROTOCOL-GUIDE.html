1

這個專案在做什麼

現在很多網站都支援 passkey：用手機、指紋或 Windows Hello 登入，不必輸入密碼。背後的標準叫 WebAuthn，是 FIDO2 規範的一部分。它的核心是數位簽章：你的裝置保管一把私鑰，網站只保存對應的公鑰；每次登入時，裝置對網站出的題目簽章，網站再用公鑰驗證。

目前 passkey 最常用的簽章演算法是 ES256（ECDSA 搭配 P-256 橢圓曲線）。足夠大的量子電腦可以用 Shor 演算法，從公鑰推算出私鑰，到時候任何人都能冒充你登入。NIST 已經公告，這類會被量子電腦破解的演算法，將在 2035 年前從 NIST 標準中移除。

本專案是一個研究性質的原型（PoC），要證明 WebAuthn 可以改用後量子簽章演算法。目前已經完成 ML-DSA（NIST FIPS 204），正在加入 FN-DSA（以 Falcon 演算法為基礎）。

我們的做法

我們不修改瀏覽器，也不修改 WebAuthn 的資料格式。網頁照常呼叫瀏覽器的 navigator.credentials API，我們在中間攔截這個呼叫，交給自己寫的軟體 authenticator 處理。網站後端（RP Server）也是自己寫的，所以雙方都認得新的演算法編號。

2

先備知識：三個密碼學概念

整個協議只建立在三個概念上，先把它們弄懂，後面的流程就很好理解。

數位簽章

一對金鑰：私鑰用來簽、公鑰用來驗。只有持有私鑰的人，才簽得出能通過驗證的簽章。網站拿著公鑰可以確認「真的是你」，卻沒辦法冒充你。

sign(私鑰, 訊息) → 簽章
verify(公鑰, 訊息, 簽章) → 對／錯

雜湊（SHA-256）

把任意長度的資料壓成 32 bytes 的「指紋」。原始資料只要改一個 byte，指紋就完全不同，而且無法從指紋反推原文。WebAuthn 用它把要簽的內容縮短成固定長度。

SHA-256("localhost")
→ 49960de5…831d9763

挑戰-回應

每次登入，網站都會出一道隨機的題目，稱為 challenge。裝置把題目一起簽進去，所以就算有人錄下舊的簽章重送，也會因為題目不同而失敗。這叫做防止重放攻擊。

RP：出題 challenge
裝置：簽 challenge ＋ 其他資料
3

WebAuthn 的角色

WebAuthn 把一次註冊或登入稱為一場儀式（ceremony），參與的角色如下。後面的流程圖都用同樣的顏色代表同一個角色。

使用者
按下註冊或登入，並通過指紋或 Windows Hello 驗證。
前端網頁
網站在瀏覽器裡執行的 JavaScript。它呼叫瀏覽器提供的 navigator.credentials.create()（註冊）與 navigator.credentials.get()（登入）。本專案是 frontend/。
瀏覽器／攔截層
正常情況下，瀏覽器負責把網頁的請求轉給 authenticator，並填入 origin。本專案由攔截層改寫這兩個 API，把請求轉給我們自己的 authenticator。填入 origin 的工作也由攔截層接手：Python bridge 和瀏覽器一樣，從呼叫者頁面的真實網址取出 origin，不採用頁面自己傳來的值；Extension 目前仍使用頁面傳來的值，但只接受 demo.yubico.com 的頁面。
Authenticator
認證器：產生並保管私鑰、執行簽章。一般是 YubiKey、手機或 Windows Hello；本專案是軟體版，支援後量子演算法。
RP Server
Relying Party（依賴方），也就是網站後端：負責出題目、驗證結果、保存公鑰。本專案是 rp_server/。

兩個用來辨識網站的值

rpId
網站的識別名稱，通常就是網域，本專案是 localhost。authenticator 會把 SHA-256(rpId) 放進簽章資料，證明這個簽章是給哪個網站的。
origin
網頁的完整來源，由協定、網域、埠組成，例如 http://localhost:3000。它會寫進 clientDataJSON，RP 會檢查它是不是自己的網站，防止釣魚網站把請求轉送過來。
4

註冊流程：建立一把新的金鑰

註冊的目的，是讓 authenticator 產生一對新的金鑰，並把公鑰交給 RP 保存。點選下方的步驟，或按「下一步」，圖上會標出對應的箭頭。

第 1 步，共 8 步
  1. 1
    前端網頁 → RP

    使用者在註冊頁輸入帳號和顯示名稱，前端呼叫 RP 的 POST /register/options。

    程式：frontend/src/pages/index.tsx
  2. 2
    RP → 前端網頁

    RP 產生 32 bytes 的隨機 challenge 並暫存起來，回傳註冊參數：rp（網站 id 與名稱）、user（使用者的隨機 user handle）、pubKeyCredParams（RP 接受的演算法，預設依序為 -49、-48、-50）、excludeCredentials（這個帳號已有的憑證，避免重複註冊）。

    程式：rp_server/app.py 的 register_options()
  3. 3
    前端網頁 → 攔截層

    前端把 base64url 字串轉回 bytes，依使用者選的演算法調整清單順序，然後呼叫 navigator.credentials.create({ publicKey })。

    程式：frontend/src/pages/index.tsx
  4. 4
    攔截層 → Authenticator

    這個 API 已經被攔截層改寫過：它把請求裡的二進位欄位轉成 base64url 字串，再交給我們的 authenticator。

    程式：authenticator/bridge.py（Python bridge）、extension/src/injected/（Extension）
  5. 5
    Authenticator 內部

    依序完成：確認 rpId 和 origin 的網域一致 → 使用者驗證（Windows Hello）→ 檢查 excludeCredentials → 照 pubKeyCredParams 的順序，選第一個自己支援的演算法 → 用 liboqs 產生金鑰對 → 產生 32 bytes 的隨機 credential ID → 保存私鑰。

    程式：authenticator/service.py 的 make_credential()
  6. 6
    Authenticator → 前端網頁

    回傳三樣東西：clientDataJSON（type 為 webauthn.create，加上 challenge 和 origin）、authenticatorData（內含 credential ID 與 COSE 格式的公鑰），以及把 authenticatorData 包成 CBOR 的 attestationObject（fmt 為 none）。

    程式：authenticator/webauthn.py
  7. 7
    前端網頁 → RP

    前端把結果轉成 base64url，送到 POST /register/verify。

    程式：frontend/src/lib/webauthn.ts 的 serializeAttestation()
  8. 8
    RP 內部

    逐項檢查：type 是 webauthn.create、challenge 是剛才發出的那一個、origin 是自己的網站、authenticatorData 開頭的 rpIdHash 等於 SHA-256(rpId)、演算法在 hosted_algorithms 裡。全部通過後，把 credential ID、公鑰、演算法和 signCount = 0 存進資料庫。

    程式：rp_server/services.py 的 verify_registration_payload()
為什麼註冊時沒有驗簽章？

本專案的 attestation 格式固定為 none，也就是 authenticator 不提供「自己是哪個廠牌型號」的證明，所以註冊時沒有可以驗證的簽章。RP 靠 challenge、origin、rpIdHash 確認這份資料屬於剛才這次註冊；之後每次登入，都必須用這把公鑰驗章成功才會通過。

5

登入流程：用私鑰簽章證明身分

登入時，authenticator 用註冊時產生的私鑰，對 RP 的題目簽章；RP 用資料庫裡的公鑰驗證。角色和註冊時一樣，差別在於資料內容。

第 1 步，共 8 步
  1. 1
    前端網頁 → RP

    使用者輸入帳號，前端呼叫 POST /authenticate/options。

    程式：frontend/src/pages/index.tsx
  2. 2
    RP → 前端網頁

    RP 找出這個帳號的所有憑證，產生新的 challenge，回傳 rpId 與 allowCredentials（可以使用的 credential ID 清單）。

    程式：rp_server/app.py 的 authenticate_options()
  3. 3
    前端網頁 → 攔截層

    前端呼叫 navigator.credentials.get({ publicKey })。

  4. 4
    攔截層 → Authenticator

    攔截層把請求轉成 JSON，交給 authenticator。

  5. 5
    Authenticator 內部

    確認 rpId 和 origin 一致 → 使用者驗證 → 從 allowCredentials 裡挑一把屬於這個網站的憑證，一把都挑不到就拒絕 → signCount 加 1 → 對 authenticatorData ‖ SHA-256(clientDataJSON) 簽章。

    程式：authenticator/service.py 的 get_assertion()
  6. 6
    Authenticator → 前端網頁

    回傳 clientDataJSON（type 為 webauthn.get）、authenticatorData（只有 37 bytes，不含公鑰）、signature 與 userHandle。

  7. 7
    前端網頁 → RP

    前端把結果送到 POST /authenticate/verify。

    程式：frontend/src/lib/webauthn.ts 的 serializeAssertion()
  8. 8
    RP 內部

    依 credential ID 找出公鑰與演算法 → 檢查 type、challenge、origin、rpIdHash → 對收到的 clientDataJSON 原始 bytes 算 SHA-256，接在 authenticatorData 後面，用公鑰驗章 → 通過就更新 signCount，登入成功。

    程式：rp_server/services.py 的 verify_authentication_payload()

allowCredentials：RP 指定這個帳號能用的鑰匙

登入時，RP 會查資料庫，把這個帳號名下登記過的所有憑證 ID 列成一份清單交給 authenticator，意思是「這個帳號只有這幾把鑰匙算數，請用其中一把簽章」。authenticator 必須遵守兩條規則：

  1. 只能用清單上的鑰匙：清單上的一把都找不到，就直接回報錯誤，不能改用其他鑰匙。
  2. 鑰匙必須屬於目前的網站：每把鑰匙都綁定在註冊時的網站上。就算清單列出了其他網站（例如 demo.yubico.com）的鑰匙 ID，也不能拿來登入這個網站。

舉例來說，假設資料庫裡登記了兩個帳號（憑證 ID 為範例值）：

帳號登記的憑證 ID演算法
alice-mwuO…ML-DSA-44
alice105Azl…ML-DSA-65

用 alice 登入時，RP 送出的清單只有 [-mwuO…]。如果使用者換了一台電腦、只重新註冊了 alice1，authenticator 裡就只剩 05Azl…。這時兩種做法的差別如下：

項目不遵守規則（Day 1 修正前的 Python 版）遵守規則（修正後）
authenticator 的做法清單上的 -mwuO… 找不到，就改用這個網站的第一把鑰匙，也就是 alice1 的 05Azl… 來簽章清單上的鑰匙一把都找不到，直接回報錯誤，不簽章
結果RP 發現這把鑰匙不屬於 alice，回傳「Unknown credential」，看不出真正的原因前端直接顯示找不到可用的憑證，原因一目了然
為什麼要用「原始 bytes」算 hash？

簽章保護的是 authenticator 送出的那串 bytes。如果 RP 先把 JSON 解析成物件，再自己重新組回去，空白、跳脫字元這類寫法就可能和原本不同（欄位順序倒是會被保留），算出來的 hash 就對不上，合法的簽章也會被當成無效。RP 原本就是這樣重組的，這是 Day 1 修正的項目。

signCount 的用途

每次登入加 1。如果 RP 發現計數沒有比上次大，可能代表金鑰被複製到另一台裝置。目前 RP 還沒有檢查是否遞增，這列在待辦清單上。

資料結構拆解

流程裡傳來傳去的資料，其實只有幾種結構。這一章逐一拆開，數值都取自本專案實際的程式。

6.1 clientDataJSON：寫明「這次在做什麼」

由 authenticator 這一側產生的一段 JSON，以 UTF-8 bytes 傳送。簽章時只會用到它的 SHA-256。

{"type":"webauthn.get","challenge":"kN3dXq6Vb3sZp1yQe9f0T2m8w4uLr7cJ5hA0gYtKx1E","origin":"http://localhost:3000","crossOrigin":false}
欄位意義
type註冊是 webauthn.create，登入是 webauthn.get。避免把註冊的資料拿去當登入用。
challengeRP 出的題目，用 base64url 編碼（上面是範例值）。RP 會確認它和自己發出的一致。
origin發出請求的網頁來源。RP 會確認它是自己的網站。
crossOrigin是否從其他網站的 iframe 發出。本專案固定為 false。

點選色塊，下方表格會標出對應的欄位。登入時只有前 37 bytes；註冊時後面還會附上憑證資料。

6.3 attestationObject：註冊結果的外包裝

用 CBOR（二進位版的 JSON）編碼的一個 map。fmt: "none" 代表不附上認證器的廠牌證明，本專案固定使用這個格式。

{
  "fmt": "none",
  "attStmt": {},
  "authData": h'49960de5…'   ← 就是 6.2 的 authenticatorData
}

6.4 COSE_Key：公鑰的標準寫法

WebAuthn 用 COSE 格式描述公鑰：一個以整數為 key 的 CBOR map。傳統的 ES256 要分別存曲線和 x、y 座標；後量子演算法的公鑰本身就是一整串 bytes，所以 RFC 9964 定義了更簡單的 AKP 金鑰類型，只放演算法編號和公鑰。

6.6 base64url：讓二進位資料能放進 JSON

WebAuthn 的 JavaScript API 用 ArrayBuffer 表示二進位資料，但 JSON 只能放文字。所以前端、攔截層與 RP 之間一律把二進位轉成 base64url：使用 A–Z、a–z、0–9、-、_ 這 64 個字元，結尾不補 =。

7

後量子演算法

後量子密碼學（PQC）指的是能抵抗量子電腦攻擊的密碼學。RSA 和橢圓曲線的安全性，建立在「因數分解」和「離散對數」很難計算上，而 Shor 演算法能在量子電腦上有效解出這兩個問題。後量子演算法改用量子電腦也沒有已知快速解法的數學問題，本專案用的兩種都屬於格（lattice）密碼學。

7.1 NIST 的後量子標準

標準演算法（前身）用途狀態
FIPS 203ML-KEM（Kyber）金鑰交換2024-08-13 發布 本專案不使用
FIPS 204ML-DSA（CRYSTALS-Dilithium）數位簽章2024-08-13 發布 已實作
FIPS 205SLH-DSA（SPHINCS+）數位簽章2024-08-13 發布 本專案不使用

7.2 本專案支援的演算法

每個演算法在 WebAuthn 裡用一個整數代表，稱為 COSE alg。RP 在 pubKeyCredParams 列出它接受的編號，authenticator 從中挑一個，寫進公鑰的 3（alg）欄位。

演算法COSE algNIST 等級公鑰簽章本專案狀態
ES256（ECDSA P-256，對照用）-7—64約 70–72不支援，會被量子破解
ML-DSA-44-4821,3122,420已完成
ML-DSA-65-4931,9523,309已完成（RP 預設優先）
ML-DSA-87-5052,5924,627已完成
FN-DSA-512-54（暫定）1897平均約 655（上限 752）實作中
FN-DSA-1024-55（暫定）51,793平均約 1,271（上限 1,462）實作中

單位為 bytes。NIST 等級 1、2、3、5 分別代表：破解它至少和「破解 AES-128」「找出 SHA-256 碰撞」「破解 AES-192」「破解 AES-256」一樣困難。

ML-DSA（FIPS 204）

由 CRYSTALS-Dilithium 標準化而來，安全性建立在模格（module lattice）上的 MLWE 與 MSIS 問題。簽章時如果算出的候選簽章可能洩漏私鑰資訊，就丟掉重算，這個設計稱為 Fiat-Shamir with Aborts。

注意：FIPS 204 的 ML-DSA 和舊版 Dilithium 不相容，因為私鑰多了 32 bytes，ML-DSA-65/87 的簽章也變長，舊版的簽章用 ML-DSA 驗不過。本專案用的是 liboqs 的 ML-DSA-44/65/87，也就是標準版。COSE 編號 -48、-49、-50 已由 RFC 9964 正式登記。

FN-DSA（Falcon）

建立在 NTRU 格上，採用 hash-then-sign：先把訊息雜湊成一個目標點，再用私鑰找出靠近它的格點當作簽章。簽章很小，但簽章過程需要精密的浮點數運算，實作難度高。

現況：FIPS 206 尚未發布，而且 NIST 已經公告會修改原規格。本專案先依原作者提交給 NIST 的第三輪規格（v1.2）實作，用 liboqs 的 Falcon-512/1024，並已用官方測試向量（KAT）驗證 100/100 筆一致。COSE 編號 -54、-55 是 IETF 草案申請中的暫定值，尚未正式分配。

程式碼地圖

8.1 兩條 authenticator 路線

動手跑一次

照順序在專案根目錄開幾個終端機執行。第一次執行時，如果電腦裡找不到 liboqs 的原生函式庫，liboqs-python 會自動下載並編譯（需要 git 和 cmake），要多等幾分鐘。

  1. 安裝依賴 
    uv sync
    cd frontend && bun install
  2. 啟動 RP Server（在根目錄；第一次會自動建立資料庫） 
    uv run flask --app rp_server.app run --port 5005 --debug
  3. 啟動前端（另開一個終端機） 
    cd frontend && bun dev
  4. 啟動 authenticator（再開一個終端機，在根目錄）。它會開一個 Chromium 視窗，在裡面註冊和登入，終端機會印出 RP 與 authenticator 的紀錄。 
    uv run python -m authenticator --url http://localhost:3000
  5. 跑測試（在根目錄；Extension 與前端的測試分別在各自的資料夾執行 bun test） 
    uv run pytest

名詞表

找不到符合的名詞，試試別的關鍵字。

WebAuthn 協議

WebAuthn
W3C 制定的網頁 API 標準，讓網站用公開金鑰密碼學取代密碼登入。
FIDO2
FIDO 聯盟的免密碼登入規範總稱，包含 WebAuthn（瀏覽器這一側）與 CTAP（瀏覽器和外接認證器之間的通訊協定）。
Passkey
給一般使用者看的名稱，指一組 WebAuthn 憑證。
Relying Party（RP，依賴方）
要驗證使用者身分的網站；本專案是 rp_server。
rpId
RP 的識別名稱，通常是網域；本專案為 localhost。
origin
網頁的來源，由協定、網域、埠組成，例如 http://localhost:3000。
Authenticator（認證器）
產生、保管私鑰並執行簽章的元件。
Platform authenticator
內建在裝置上的認證器，例如 Windows Hello、Touch ID。本專案回報 authenticatorAttachment 為 platform。
Ceremony（儀式）
WebAuthn 對一次註冊或登入的稱呼。
Registration／Attestation（註冊）
建立新憑證的儀式，對應 navigator.credentials.create()。
Authentication／Assertion（登入／斷言）
用既有憑證登入的儀式，對應 navigator.credentials.get()；authenticator 回傳的簽章結果稱為 assertion。
Credential（憑證）
一組金鑰對，加上 credential ID、所屬網站等資料。
Credential ID
憑證的唯一識別碼；本專案為 32 bytes 隨機值。
User handle
RP 指派給使用者的隨機 ID，不是帳號名稱。
Challenge
RP 每次產生的隨機值，簽章時一起被簽進去，用來防止重放攻擊。
pubKeyCredParams
RP 接受的演算法清單，依偏好排序。
excludeCredentials
註冊時列出已存在的憑證，避免同一個 authenticator 重複註冊。
allowCredentials
登入時，RP 列出這個帳號名下登記過的憑證 ID；authenticator 只能從中挑選屬於這個網站的憑證，一把都找不到就必須回報錯誤（例子見第 5 章）。
UP（User Presence）
使用者在場，例如按了按鈕；flags 中的 0x01。
UV（User Verification）
使用者通過驗證，例如指紋、PIN、Windows Hello；flags 中的 0x04。
signCount
簽章計數器，每次登入加 1，用來偵測被複製的認證器。
AAGUID
認證器型號的 16 bytes 識別碼；本專案全為 0。
Attestation format none
不提供認證器廠牌型號的證明；本專案固定使用。

資料格式

clientDataJSON
記錄這次操作的 JSON，包含 type、challenge、origin；以 UTF-8 bytes 傳送。
authenticatorData（authData）
authenticator 產生的二進位資料：rpIdHash、flags、signCount，註冊時還附上憑證資料。
attestationObject
註冊時回傳的 CBOR 結構，包含 fmt、attStmt、authData。
rpIdHash
SHA-256(rpId)，位於 authenticatorData 開頭 32 bytes。
CBOR
二進位版的 JSON（RFC 8949），WebAuthn 用它編碼 attestationObject 與公鑰。
COSE
用 CBOR 表示金鑰與演算法的標準；WebAuthn 的公鑰採用 COSE_Key 格式。
COSE_Key
用整數為 key 的 CBOR map 表示公鑰，例如 {1: kty, 3: alg, -1: pub}。
kty
COSE_Key 的金鑰類型欄位（標籤 1），例如 2 = EC2、7 = AKP。
AKP（Algorithm Key Pair）
RFC 9964 定義的金鑰類型（kty = 7），用在公鑰是一整串 bytes 的後量子演算法。
COSE alg
演算法的整數編號，例如 -7 = ES256、-48 = ML-DSA-44。
base64url
把二進位轉成可放進網址與 JSON 的文字：用 - 和 _，結尾不補 =。

密碼學

數位簽章
用私鑰簽、用公鑰驗，證明資料來自私鑰持有者且沒有被竄改。
SHA-256
輸出 32 bytes 的雜湊函數。
PQC（後量子密碼學）
能抵抗量子電腦攻擊的密碼學。
Shor 演算法
量子演算法，能有效破解 RSA 與橢圓曲線密碼。
格（Lattice）密碼學
建立在高維度格子相關數學問題上的密碼學；ML-DSA 與 FN-DSA 都屬於這類。
ML-DSA
Module-Lattice-Based Digital Signature Algorithm，NIST FIPS 204，由 CRYSTALS-Dilithium 標準化而來。
CRYSTALS-Dilithium
ML-DSA 的前身（NIST 第三輪版本），和 ML-DSA 不相容。
FN-DSA
FFT over NTRU-Lattice-Based Digital Signature Algorithm，預定的 NIST FIPS 206，以 Falcon 為基礎。
Falcon
FN-DSA 的前身；本專案使用原作者提交給 NIST 的第三輪規格 v1.2。
NTRU
一種格密碼結構，是 Falcon 的數學基礎。
Hedged signing
每次簽章都加入新的隨機數，同一則訊息每次簽出不同的簽章；ML-DSA 預設採用。
Context string（ctx）
FIPS 204 加入的簽章參數，最長 255 bytes；RFC 9964 規定在 COSE 中必須為空字串。
NIST 安全等級
1、2、3、5 級，分別對應破解 AES-128、找出 SHA-256 碰撞、破解 AES-192、破解 AES-256 所需的計算量。
KAT（Known Answer Test）
用固定輸入和官方公布的預期輸出，驗證實作是否正確的測試。
ES256
ECDSA 搭配 P-256 曲線與 SHA-256，WebAuthn 最常見的傳統演算法（COSE -7）。

NIST
美國國家標準與技術研究院，主持後量子密碼標準化。

W3C
制定 WebAuthn 的網頁標準組織。

常見問題

為什麼不直接修改瀏覽器？

修改瀏覽器的成本太高，也無法讓一般使用者安裝。改寫 navigator.credentials 可以在不動瀏覽器的前提下，完整走完 WebAuthn 流程。代價是只有接受這些新演算法編號的 RP，例如我們自己的 rp_server 或 Yubico 的示範網站，才能驗證這些簽章。

ML-DSA 和 Dilithium 可以混用嗎？

不行。FIPS 204 修改了金鑰與簽章的計算方式，舊版 Dilithium 的簽章用 ML-DSA 驗不過。本專案用的是 liboqs 的 ML-DSA-44/65/87，不是 Dilithium2/3/5。

-54、-55 是正式的演算法編號嗎？

不是。它們是 IETF 草案 draft-ietf-cose-falcon 申請中的值，IANA 尚未分配。FIPS 206 發布後，實作和編號可能都要調整，用舊版註冊的憑證也要重新註冊。

Falcon 的簽章為什麼長度不固定？

Falcon 的簽章經過壓縮編碼，長度依內容而定：Falcon-512 平均約 655 bytes，上限 752。規格也定義了補 0 到固定長度（666 bytes）的格式，liboqs 稱為 Falcon-padded-512。

RP 為什麼要檢查 origin 和 rpIdHash？

檢查 origin，是確認請求來自自己的網頁，而不是把請求轉送過來的釣魚網站；檢查 rpIdHash，是確認 authenticator 簽章時認定的網站就是自己。兩者都對了，簽章才有意義。

liboqs 可以用在正式環境嗎？

liboqs 官方說明它供研究與原型使用，不建議用在正式環境。本專案是研究原型，符合這個定位。
